## 7. Natural-Boundary Experimental Question

> Starting from what `TurnFrame` and the currently-wired call paths actually produce today (§3–§4) — not from an idealized or benchmark-oracle Step-1 output — what does the existing deterministic RAR resolver (`rar_deterministic.py`, unmodified) resolve reliably by itself, what information does it actually require to do so, and where does that reliability measurably end?

This is deliberately **not**: a test of whether RAR *should* do segmentation (§ task framing, explicit exclusion); a rescue attempt; a Needle/Qwen qualification; or a final Step-2 architecture decision. It is a measurement of the existing system's own honest reach, given only what upstream mechanisms genuinely, deterministically produce today.

## 8. Proposed Benchmark Construction

The exact conditions are derived from §3–§4's evidence, not imposed in advance. Three evidence-driven design decisions follow directly from the code inspection above:

1. **The benchmark must start from raw turn text, not from a pre-written `reference_expression` string.** Every prior RAR benchmark (Stage 2 through 4B-C) started downstream of segmentation; this experiment's entire purpose is to measure the boundary that starts *before* that point, so it must run raw text through the real `build_turn_frame()` and observe what `candidate_references` (if any) come out, before ever constructing an `RARQuery`.
2. **The candidate pool cannot be claimed as "naturally available" — it must be explicitly labeled as supplied, and its supply method itself becomes a tested variable**, because §4 confirmed `ActiveContext` has no production builder. Rather than silently treating the candidate pool as a given (as every prior stage did), this experiment should test RAR's behavior across *at least two* candidate-pool-availability conditions: candidates present and correctly scoped vs. candidates present but containing distractors vs. no candidate pool available at all (forcing the `NO_CANDIDATE`/similar failure classification RAR's Stage 2 report already named). This directly operationalizes "what information does RAR actually require" rather than assuming the answer.
3. **`recency_hint`, `negation_spans`, and `target_type_hint` must each be tested both in their real (narrow/absent) production form and in an idealized oracle form, with the gap between the two conditions reported as its own measurement** — since §4 established that real wired `recency_hint` only ever equals `"same"` or `None`, real `negation_spans` is always turn-global, and real `target_type_hint` never exists at all. Measuring RAR only under oracle conditions (as every prior stage did) cannot answer this experiment's question; measuring only under real conditions cannot show what *would* change if these fields were properly derived. Both are needed to attribute failures correctly (§9's failure taxonomy exists specifically to make this attribution possible).

**Amendment (`docs/plans/M35_URIV1_PRE_RAR_CANDIDATE_ANCHOR_SOURCE_AUDIT.md`, §9/§11):** for any C1/C2 fixture whose true reference is attachment-flavored ("the attached PDF," "this spreadsheet"), the candidate objects should be shaped after `uri_core/core/file_store.py`'s real, live `StoredFile.to_reference()` schema (`file_id`, `filename`, `media_type`, `size_bytes`) rather than an arbitrary invented schema — this real data shape exists and is production-verified, even though no import path currently carries it into `uri_v1/turn/`. For any candidate pool representing a general artifact/entity beyond file attachments, no equivalent real data shape exists anywhere in the repository (confirmed by the source audit); those remain necessarily synthetic, unchanged from the original design below.

**Fixture authorship independence (anti-contamination, per §"Safety/anti-contamination requirements" and reusing Stage 4B-A's lesson):** the raw-turn fixtures for this experiment must be authored by someone (or some process) that has not read `rar_deterministic.py`'s internals — genuine independence, following Stage 4B-A's manifest methodology, not Stage 3's "procedurally independent but not blind" shortfall. Because this experiment additionally needs raw text (not pre-segmented expressions), the fixture author also should not read `turn_frame_builder.py`'s exact pattern lists, or the fixtures would risk being unconsciously shaped to match (or deliberately avoid) `TurnFrame`'s known vocabulary — the opposite of what a natural-boundary measurement needs. If genuine blindness to `turn_frame_builder.py` cannot be achieved in practice (the same author may need to know URI's domain vocabulary to write realistic office-work turns), this limitation must be stated explicitly in the eventual results report rather than the benchmark being called "blind."

## 9. Proposed Experimental Conditions

Derived from §3–§4's actual code shape, not a fixed ladder imposed in advance. The natural structure that falls out of the evidence is **two independent axes** (what Step 1 really provides vs. what the candidate pool really provides), not a single linear ladder:

**Axis 1 — Step-1 input realism** (what feeds `reference_expression`/`recency_hint`/`negation_spans`/`target_type_hint`):
- **S1 — Real wired path:** raw text → real `build_turn_frame()` → real `candidate_references` (whatever the 21-pattern matcher actually finds, including finding nothing) → real ad-hoc `recency_hint` (`"same"`/`None` only) → real turn-global `negation_spans` → `target_type_hint` always absent (matches `lfm_semantic_decoder.py`'s actual current production shape).
- **S2 — Oracle/idealized:** the same raw turns, but with a hand-labeled true `reference_expression` (whatever a human reader would actually extract, unconstrained by `TurnFrame`'s vocabulary), a correctly-scoped `recency_hint`, a per-reference-scoped `negation_spans`, and a supplied `target_type_hint` — i.e., every prior RAR benchmark's implicit condition, made explicit here as the upper-bound comparison point.

**Axis 2 — Candidate-pool realism** (since §4 confirmed there is no real builder):
- **C1 — Clean candidate pool:** exactly the candidates a correct resolution needs, no distractors (matches Stage 2/3/4's implicit condition).
- **C2 — Realistic candidate pool:** the true candidate plus plausible distractors of the same type (closer to Stage 4B's actual condition, which is where wrong bindings first appeared).
- **C3 — No candidate pool supplied:** tests RAR's behavior when `ActiveContext`'s real absence (§4) is respected rather than papered over — this condition did not exist in any prior RAR benchmark, all of which always supplied *some* candidate pool.

**Amendment (`docs/plans/M35_URIV1_PRE_RAR_CANDIDATE_ANCHOR_SOURCE_AUDIT.md`, §6/§9/§11):** C3 is not merely a synthetic worst-case control — a dedicated source audit confirmed, via a repository-wide zero-import check between `uri_core/` (the real, live, production-traffic-serving backend, confirmed by a prior independently-verified 130-test milestone regression) and `uri_v1/turn/`, that C3 is the literal current condition of the `uri_v1/turn/` pipeline if invoked today. In the active production backend (`uri_core/`), requests do not invoke `uri_v1/turn/` RAR at all. `uri_core` possesses real, durable, live candidate/anchor-relevant state (a file/attachment store, a post-action result resolver, workflow-pause tracking, conversation history, an assembled turn-context projection reached by every real request by default) — none of which reaches `uri_v1/turn/`'s RAR calls through any code path that exists today. The results report should present C3 as "what actually happens if the uri_v1 pipeline is invoked today," not as an artificial floor or as an active failure in live uri_core traffic.

The resulting condition grid is **S1×C1, S1×C2, S1×C3, S2×C1, S2×C2** (S2×C3 is degenerate/uninformative — an oracle reference expression with zero candidates has only one possible RAR outcome and adds no signal). This is **not** the ladder sketched in the task prompt ("raw → plus surface info → plus other info → existing RAR") because the evidence shows the real dependency structure is two-dimensional (input realism × candidate realism), not a single accumulating ladder — imposing a one-dimensional ladder would hide exactly the interaction (e.g., does a realistic candidate pool matter more or less when the reference expression is also realistic?) this experiment exists to observe.

Each condition is run against the **existing, unmodified** `rar_deterministic.py` — no code changes, per the task's explicit restraint.

## 10. Failure Taxonomy

Starting from the categories the task suggested, refined against what §3–§4's evidence shows is actually possible given the real code paths (new categories added where evidence justifies them; suggested categories not force-fit where they don't apply):

| Class | Definition | Distinguishing evidence needed |
|---|---|---|
| `SILENT_STEP1_MISS` | The true reference expression exists in the raw turn but falls outside `TurnFrame`'s 21-pattern vocabulary — RAR is **never even invoked**, because no `candidate_references` entry was produced. This is a Step-1 recall failure, not a RAR failure, and is invisible to any benchmark that starts from a pre-written `reference_expression` (i.e., invisible to every prior RAR stage). | Only observable under condition S1 (real `TurnFrame`), by comparing what S1 extracted against the S2 oracle label for the same raw turn. |
| `MISSING_CANDIDATE_CONTEXT` | A `reference_expression` was correctly identified (S1 or S2), but no candidate pool was available to resolve it against (condition C3), or the correct candidate was never in the supplied pool. | RAR's own `UNKNOWN`/`NO_CANDIDATE`-style outcome under C3, or a candidate genuinely absent from a C1/C2 pool. |
| `CORRECT_ABSTENTION` | RAR returns `AMBIGUOUS` or `UNKNOWN` and that is the genuinely correct answer (a real human reader would also be unable to resolve it, or multiple candidates are genuinely equally valid). Counted as success, not failure, per RAR's own stated invariants and the prior reconstruction's "safe abstention is correct behaviour" framing. | Requires ground truth to mark the *expected* outcome as `AMBIGUOUS`/`UNKNOWN`, not just observing that RAR abstained. |
| `INCORRECT_CONFIDENT_BINDING` | RAR resolves to a specific candidate ID, and that candidate is wrong (the prior reconstruction's "wrong binding" class — first observed only in Stage 4B). | Ground-truth correct candidate ID differs from RAR's returned `candidate_id`. |
| `UNSAFE_OVER-ELIMINATION` | A correct candidate is eliminated by negation/contrast logic (Level 4a) because `negation_spans` is turn-global rather than scoped to the specific reference/clause (§4's confirmed real-production limitation) — a distinct, attributable sub-class of incorrect confident binding or incorrect abstention, traceable specifically to unscoped negation, not to any other cause. | Compare S1 (turn-global negation, real production shape) vs. S2 (per-reference-scoped negation, oracle) outcomes on the same fixture; a flip specifically attributable to negation scope is this class. |
| `RECENCY_SIGNAL_UNREACHABLE` | RAR would resolve correctly *if* given a `recency_hint` beyond `"same"`/`None` (e.g. "latest", "current", "previous" — which Stage 4's RC-1 taught the resolver to use), but no production call path ever supplies such a value (§4). | Compare S1 (real, narrow `recency_hint` derivation) vs. S2 (oracle `recency_hint`) outcomes on fixtures whose ground truth depends on ordinal/temporal binding. |
| `TYPE_DISCRIMINATION_UNREACHABLE` | Same pattern as above, specifically for `target_type_hint`, which §4 confirmed has zero production derivation anywhere. | Compare S1 vs. S2 on fixtures whose ground truth depends on type filtering (Level 4b). |
| `DISTRACTOR_CONFUSION` | RAR resolves incorrectly specifically because a realistic distractor was present in the candidate pool (condition C2) that would not have caused an error under a clean pool (condition C1) on the otherwise-identical fixture. | Compare C1 vs. C2 outcomes on matched fixtures. |
| `INVENTED_CANDIDATE` | RAR returns a `candidate_id` not present in the supplied candidate set — the one failure class that has been `0` across every prior stage including Stage 4B's wrong-binding cases; retained here as a hard safety check, expected to remain `0`. | `validate_rar_resolution`'s own contract check; a violation here would itself be the most severe possible finding. |
| `UNSUPPORTED_INPUT_TYPE` | The raw turn contains a reference type RAR's cascade has no level for at all (e.g., a reference resolved only via genuine world/domain knowledge rather than any lexical/structural signal — the "SEMANTIC_DISCRIMINATION" class Stage 2's own report already named as the sole class it considered to genuinely require AI). | Cases where even the S2×C1 oracle-input condition cannot produce a correct RAR resolution because no level of the cascade is designed to handle the signal type present. |
| *(reserved)* | Any additional failure mode the actual benchmark run surfaces and that does not fit the above — to be named and added at execution time, not forced into an existing bucket, per the task's explicit instruction. | N/A — this row exists to license honest taxonomy growth during the real run, which this design-only phase cannot pre-populate. |

## 11. Measurements

No acceptance thresholds are invented (per governing `SKILL.md`'s Evidence Over Assumption rule and this task's explicit instruction); every gate is `UNMEASURED` unless a prior stage established one and that same measurement is being repeated identically.

Minimum capture set per fixture × condition-cell:
- Outcome: `RESOLVED` / `AMBIGUOUS` / `UNKNOWN`, and whether that matches ground truth.
- `INVENTED_CANDIDATE` check (hard 0 expectation, per `validate_rar_resolution`).
- Failure classification (§10), including which axis (S1 vs S2, C1 vs C2 vs C3) the fixture was run under.
- Which RAR cascade level actually produced the outcome (`rule_used`/level attribution — already emitted by `DeterministicRARTrace`).
- Latency (already emitted by the resolver; expect sub-millisecond based on every prior stage, but `NOT_MEASURED` claims are not to be repeated as fresh measurement without an actual run).
- For S1-condition fixtures specifically: whether `TurnFrame.candidate_references` found *any* candidate for the true reference expression at all (this is what makes `SILENT_STEP1_MISS` observable — no prior stage captured this).
- Cross-tabulation of outcome by (Axis 1 × Axis 2) cell, to make the interaction effect (§9) directly readable rather than only reporting marginal totals.

Additional measurements the inspected implementation makes uniquely available and worth capturing (beyond the task's minimum list): `eliminated_candidate_ids` and `candidate_scores` (both already fields on `DeterministicRARTrace`) — useful for diagnosing *why* Level 6's discriminating-term scoring did or didn't separate a realistic distractor (condition C2) from the true candidate, without needing to re-derive that from the raw resolution outcome alone.

## 12. Anti-Contamination / Independence Controls

- **No production code hardcoded to benchmark cases** — the explicit anti-pattern this task named from A2.8D's `fast_path_gate.py` contamination. The natural-boundary benchmark introduces no new production file at all in this design phase; when eventually implemented, its fixtures and any harness/runner code must stay in benchmark-only files (mirroring `rar_stage4b_independent_fixtures.py`'s location, not `uri_v1/edge/fast_path_gate.py`'s).
- **No expected-answer field may influence runtime decision logic** — `rar_deterministic.py` is run completely unmodified; ground-truth labels exist only in the fixture/scoring layer, exactly as `RARFixture`'s existing shape already separates `query` from `expected_resolution` in `rar_contracts.py`.
- **Fixture authorship independence, reusing Stage 4B-A's method**: the fixture author should construct raw-turn fixtures (and their S2 oracle labels) without reading `rar_deterministic.py`'s resolution logic, following the same manifest-and-confirm methodology Stage 4B-A used (author confirms in writing which files were and weren't read before construction). Provenance for every reused fixture (from Stage 2/3/4/4B, if any are reused as raw-turn *seeds* by reconstructing plausible original text) must be explicitly stated, not assumed.
- **Explicit limitation disclosure, not a false "blind" label**: as noted in §8, true blindness to `turn_frame_builder.py`'s specific pattern lists may not be achievable if the same author needs realistic domain knowledge to write the raw turns. If so, state this limitation plainly in the eventual results report (following Stage 3's own self-disclosed shortfall as the precedent for how to report this honestly) rather than calling the benchmark "blind."
- **Separation of benchmark authorship from implementation authorship "as far as practical"**: given RAR's implementation is already frozen/unmodified for this experiment, the main practical control is that whoever writes the S1-vs-S2 raw-turn/oracle-label pairs does not simultaneously read or modify `rar_deterministic.py`, `turn_frame_builder.py`, or `active_context.py` during construction.

## 13. What This Experiment Explicitly Cannot Conclude

- It cannot conclude that URI v1 needs a deterministic reference-expression segmenter, a tiny model, Needle, Qwen, Graphify, or any other new mechanism — per the task's explicit restraint, this experiment only records *what information RAR needs and where it currently comes from*, not *who should provide it*.
- It cannot conclude a final Step-2 architecture, since Step 1's broader goal/intent/operation decoding (already qualified separately via A2.7/Qwen3.5-9B resident) is out of scope here.
- It cannot conclude that `TurnFrame`'s 21-pattern vocabulary is "wrong" or should be expanded — only that its recall against real reference expressions is currently unmeasured; expanding it is a later, separate decision.
- It cannot conclude anything about Needle 3's narrow-auxiliary-role candidacy (the prior reconstruction's Candidate 1) or about building a segmenter (Candidate 2) — this experiment's results are a prerequisite input to *deciding* between those two candidates, not a substitute for that decision.
- It cannot conclude that `ActiveContext`'s missing production builder should be built the way legacy `TurnState.active_pointer` does it — §6 records that as a design precedent worth future consideration, not a decision this experiment makes or needs to make.
- It cannot validate `rar_deterministic.py`'s DET-ONLY (levels 0/1, deterministic-anchor) performance in a real production setting, because §4 confirmed no production call path currently populates `RARDeterministicAnchor` at all — so real deterministic-anchor performance remains as unmeasured after this experiment as before it, unless the benchmark design is extended to construct that condition explicitly (which the S1×C1/C2 conditions as designed do not, since they mirror the real `lfm_semantic_decoder.py` path, which never populates it either — this is itself a finding worth flagging, not a design flaw to silently fix by inventing a synthetic condition beyond what real code paths produce).
- **It cannot conclude that `uri_core`'s real candidate/anchor sources (`FileStore`, `CapabilityContextResolver`, `TurnState`) should be wired into `uri_v1/turn/`** — the source audit (`M35_URIV1_PRE_RAR_CANDIDATE_ANCHOR_SOURCE_AUDIT.md`) confirmed these sources exist and are live in `uri_core/`, but wiring them is a separate future architectural decision, explicitly out of scope for both that audit and this experiment.

## 15. Frozen Implementation Blueprint for the Later Experimental Run

This section freezes the design so a later implementation session does not need to re-derive it, per this task's own required output. **Not implemented in this session.**

1. **Fixture set:** a new file (not reusing any existing RAR fixture file, per §5/§8) of raw, realistic office-work user turns — target size to be set by whoever implements this (no threshold invented here, per §11), each turn hand-labeled with: (a) the S2 oracle `reference_expression`(s) a human would extract, (b) the correctly-scoped `recency_hint` and per-reference `negation_spans`, (c) `target_type_hint` where applicable, (d) the ground-truth correct candidate ID or `AMBIGUOUS`/`UNKNOWN` expected outcome, and (e) which failure class (§10) would explain a wrong result, pre-annotated where determinable in advance.
2. **Runner shape:** for each fixture, first run raw text through the real, unmodified `build_turn_frame()` to capture the real S1 `candidate_references` (recording whether the true reference was found at all — this produces the `SILENT_STEP1_MISS` signal). Then construct both S1 and S2 `RARQuery` objects (varying only the input-realism axis) crossed with C1/C2/C3 candidate-pool conditions, per the grid in §9, and call the real, unmodified `resolve_rar_deterministic_extended()` for each of the five cells.
3. **Candidate pools (C1/C2/C3):** authored alongside the fixtures by the same independent author, with C2's distractors constructed to be plausible-but-wrong along the same axes RAR's Level 4b/6 discriminate on (type, title similarity, recency), not arbitrary noise — this makes `DISTRACTOR_CONFUSION` findings attributable to genuine discrimination difficulty rather than to unrealistic test construction.
4. **Scoring:** apply §10's taxonomy classification logic as a separate scoring script that reads `DeterministicRARTrace` output plus the fixture's ground truth — never inside `rar_deterministic.py` itself, and never inside any file that also defines fixture data (mirroring the C2/C3 point above and the A2.8D anti-pattern warning).
5. **Reporting shape:** a results report following this document's own PROVEN/OBSERVED/HYPOTHESIS/UNMEASURED/UNKNOWN discipline, with the §9 cross-tabulation (S1×C1, S1×C2, S1×C3, S2×C1, S2×C2) as its central table, and explicit per-failure-class counts from §10.
6. **Explicit non-goals restated for the implementer:** do not modify `rar_deterministic.py`, `turn_frame_builder.py`, or `active_context.py` to make numbers look better; do not build a general segmenter to backfill `TurnFrame`'s gaps; do not invoke Needle, Qwen, or any model; do not wire anything into production; do not continue or touch A2.8D or A2.9.

## Summary for User Review

**Discovered Step-1 → RAR boundary:** narrower than the prior reconstruction implied in one specific respect and confirmed in another. A real, deterministic, closed-vocabulary (21-pattern) reference-expression extractor exists in `TurnFrame` and **is** wired to RAR in one real production call path (`lfm_semantic_decoder.py`) — this corrects the prior document's implication that no segmentation exists at all. But the candidate pool RAR resolves against (`ActiveContext`) has **no production builder anywhere in the repository** — confirmed, not merely suspected — and `recency_hint`/`target_type_hint`/scoped-`negation_spans` are each either absent or far narrower in real wired code than in any qualification benchmark. RAR's most-proven cascade levels (0/1, deterministic-anchor) are **never actually exercised by any current production call path**.

**Major oracle/artificial-input dependencies found:** the candidate pool (100% benchmark-supplied, no builder exists); `target_type_hint` (100% benchmark-supplied); `deterministic_anchor` fields (100% benchmark-supplied, and unused even by the one real wired call path); `recency_hint` beyond the literal `"same"`/`"same thing"` check (qualified by Stage 4's RC-1 refinement but never reachable in production); per-reference-scoped `negation_spans` (RAR was only ever qualified against turn-global negation in production, contradicting several qualification stages' implicit assumption of proper scoping).

**Proposed experimental conditions:** a two-axis grid (Step-1 input realism: real-wired vs. oracle; candidate-pool realism: clean vs. realistic-with-distractors vs. absent) run against the existing, unmodified RAR resolver, starting from raw text through the real `build_turn_frame()` rather than a pre-segmented reference expression — the first RAR evaluation to do so.

**Legacy comparison:** no legacy mechanism solves RAR's actual job (re-confirms the earlier ARN-naming-collision finding, now from the legacy side); the two reusable items found are design principles for later work (`TurnState`'s re-derive-fresh-from-session-state pattern for a future `ActiveContext` builder, and confirmation that abstention-over-guessing is a repeatedly-validated stance), not code to import now.
