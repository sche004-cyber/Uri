# C3 — Client worker and private persistence baseline

FROZEN FOR IMPLEMENTATION — PROVISIONAL — AWAITING INDEPENDENT REVIEW.

Implements the approved C3 dependency on C2, using the C2 store method contract and existing stores. Each new client has a fresh, current-account ACL-protected synthetic installation, distinct private/workspace/config/secure/home/temp roots, pinned server identity, and DPAPI-protected principal/pairing/session and credential-store secrets. Existing account homes, preferences and production state are never imported.

The worker uses bounded four-byte big-endian length-prefixed UTF-8 JSON frames (2 MiB cap), stdin/stdout for the trusted owning application and stderr for safe operational errors. Commands are strict identity, snapshot, consent, commit and close requests. Identity proves a fresh nonce with a client key pinned in its manifest. A lifetime installation mutex prevents duplicate workers. The launcher validates exact source/interpreter/state/worker identity before launch and never starts the server or models. Until C6 supplies a qualified UI binary and manifest consumer, only explicitly selected headless development operation is available; it must not claim desktop launch parity.

All private store constructors and methods run only in the worker with explicit client paths. DTO serialization reuses dataclasses and existing session serialization; files expose references, never native paths. Credential reads and FileStore.path_for remain local-only. Method signatures are bound against actual methods before invocation. Session/file owner checks precede local reads; output schemas and limits apply before transfer.

The client single-writer mutex and private SQLite journal cover store versions, exact projected read sets, consent, intent and durable receipts. Commit validates binding, allowlisted mutation method, payload/projection digests, current versions and explicit local consent. It records PREPARED intent and private backup copies before running existing validated store methods. Local mutations never invoke tools or external services. Successful receipt and versions are committed durably; only then is success returned. A pending journal after crash restores private files into the same new synthetic client root and marks the transaction rolled back; it never replays a method or external side effect. A repeated operation returns the saved receipt only for an identical mutation digest. CAS conflicts and recovery remain explicit.

This journal provides recoverable multi-store application, not simultaneous crash-atomic visibility to arbitrary external readers. Only this worker is an authorized writer; external file changes invalidate fresh projection digests. SQLite graph reads/writes retain the original store's native transactions. Backups include only this synthetic client's private stores, never another client's data, secure account homes or production roots. Restore operations verify absolute source/target containment within this installation and use native filesystem APIs.

Approval/operation/external-service lifecycle mutations retain their existing validators. Client UI consent does not expand server grants or qualify a harness; C4 tickets/claim receipts remain separate. No server or model output can issue the local consent command over HTTP.

Gates: two independent clients; private file/session/graph/approval isolation; framed protocol size/truncation/malformed/unknown-field rejection; source/interpreter/server pin rejection; worker signed identity and duplicate launch exclusion; no server/model startup; consent refusal, stale versions/projections, identical/conflicting replay, multi-store failure rollback and interrupted-intent recovery; existing store and Core regressions. UI, native harness live qualification and production migration remain separate later gates.
