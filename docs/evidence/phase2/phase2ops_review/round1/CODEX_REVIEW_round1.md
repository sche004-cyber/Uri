## B. Implementation attacks

**Approval and authority.** `execution_proposal` binds client/session/turn, kind/provider/model, capability, argument digest and server approval digest in its proposal digest (`execution.py:47-66`). `execution_begin` recomputes both digests from the pending worker turn and drops a wrong echo (`:270-287`); the frozen `TurnRunner.decide` still sends the server approval digest, and the signed ticket, journal, claim and selection checks still precede bridge execution (`runner.py:35-67`; `uri_core/client_runtime/turn_runner.py`, `decide`/`_execute`). A replay finds no pending turn. Typed text calls `turn_start`, never `execution_begin`; the UI has a separate approve button (`supervised_execution_screen.dart:213-225,497-504`). I source-traced these properties; the focused tests in `tests/phase2ops/test_lifecycle.py` were read, not independently run. The register and UI have no ticket authority. **The card does not render `approval_request.arguments` verbatim**, although C6 explicitly requires that (`C6_UI_INTEGRATION_CONTRACT.md`, integration contract). It renders instruction, file, capability and other summaries (`supervised_execution_screen.dart:330-356`), while the full `arguments` object is retained only in the Dart model (`supervised_runtime.dart:63-64`). The digest protects bytes sent to the worker, but a user cannot inspect every approved argument on this card.

**Lifecycle and cancellation.** In the ordinary execution path, only `SETTLED_VERIFIED` maps to `completed`; unrecognized codes become `uncertain`, and an exception after leaving `queued` becomes `uncertain` (`execution.py:307-369`). `running_at` is set by the dispatch hook before `bridge.execute`, so it means dispatch reached the bridge, not that a process was spawned (`execution.py:314-320`; `runner.py:62-64`). `starting_at` is set when the ticket validates, before online claim (`runner.py:41-47`; frozen `_execute`), so its documented “ticket verified” meaning is accurate. A queued exception is `failed`; approval/claim/settle transport loss after that is `uncertain`. `cancel` sets a worker flag and calls `bridge.cancel` once a task id exists; the bridge checks the flag before admission, after admission and after an attempt, and its supervisor uses a job-backed kill path (`execution.py:303-320,371-404`; `bridge.py:220-298,313-330`; `supervisor.py:352-360`). The close and stdin EOF paths call withdrawal (`run_uri_supervised_worker.py:218-229`). Tests and real-process logs claim preapproval, predispatch, running, descendant, terminal, close and crash coverage. I did not independently run those process tests or verify Windows job membership; I found no source-supported re-admission after a cancellation.

**Reconnect, durable truth and corruption.** `ExecutionRegister` writes atomically under `control/supervisor/executions/` and restart changes active records to uncertain after journal recovery (`execution.py:125-217`). Calling frozen `ExecutionJournal.recover()` is consistent with its rule: it changes `claim_requested`/`claimed` operations to `execution_uncertain`; it does not launch an executor (`uri_core/client_runtime/execution_journal.py`, `recover`). The bridge acquires a single-supervisor lock (`supervisor.py:78-101`) and revokes unfinished authorizations at start (`bridge.py:106-173`); two simultaneous workers cannot both own that supervisor ledger. The status path does re-read ledger, journal and server, and server loss is rendered as `SERVER_STATUS_UNAVAILABLE`, not an invented server state (`execution.py:243-267`). **But the register's own state is not checked against any of those facts.** My direct-import probe wrote a valid-schema JSON record with `state=completed`, `code=SETTLED_VERIFIED`, no task or journal entry, and a server callback reporting `execution_uncertain`. `ExecutionController.status()` returned that record as `completed` together with `ledger=None`, `journal=None`, `server_turn.state=execution_uncertain`. `list()` likewise relays the record state (`:251-255`). This contradicts the claimed “completed only from SETTLED_VERIFIED” guarantee on reconnect and allows valid JSON corruption or local record alteration to show false success; the UI treats the register state as terminal (`supervised_runtime.dart:210-216`; `supervised_execution_screen.dart:383-403`). A second direct probe used valid-schema JSON missing `execution_id`: `ExecutionRegister.list()` raised `KeyError`, so `reconcile_restart()` can abort worker construction and the UI cannot list histories (`execution.py:166-185,206-217`). The existing unreadable-record test covers invalid JSON, not valid but malformed JSON (`tests/phase2ops/test_reconnect.py:93-103`). These probes used only synthetic state under `work/c1/reviewer_ops_round1` and never touched a real client profile.

**Receipt, Phase 2D and fake harness.** The generated record includes user task text, proposal arguments/digests, timestamps, settlement code, limited evidence fields and task id, but the controller does not insert a signed ticket, authorization token or credential (`execution.py:289-296,322-335,243-255`). The record is local client data and may contain private user text; it must be protected as such. The Phase 2D binding still checks signed client-bound records, expiry, evidence hash/content, launch chain and per-run revalidation (`qualification.py:272-281,366-419,459-485`; `bridge.py:190-220`). R3-1/R3-2 repair now rejects absent or malformed fixture model lists with `QualificationError`, while native evidence still binds the single probed model (`qualification.py:379-396`). I inspected those production checks and test definitions; I did not recreate the full Phase 2D attack matrix in this round. The `'(fake scenario: X)'` parser exists only inside `tests/phase2b/helpers/fake_harness.py:21-35`; URI sends user instructions to the selected executor as stdin (`bridge.py:248-249,281-285`), but URI production code does not interpret this marker. A real model may read such text as ordinary instruction, which is not the fake harness scenario switch.

**Flutter entry.** `app.dart:344-349` mounts `SupervisedExecutionEntry` on the real Tasks destination. The entry appears only with the opt-in file; `fromManifest` spawns `scripts/run_uri_supervised_worker.py` from the manifest source root, passes no fixture flag and checks the worker profile before use (`supervised_runtime.dart:283-365`; `supervised_execution_screen.dart:520-549`). The screen locks executor choice while a card is pending, echoes both digests on approval, polls status, offers cancellation and shows uncertainty without automatic fallback (`supervised_execution_screen.dart:213-269,330-418,464-505`). This is actual URI Flutter code on an **opt-in parallel Tasks route**; it does not replace Chat's legacy `/ask` or the frozen Settings paired screen. C6 still lists Chat integration and a pinned UI build as remaining cutover work (`C6_UI_INTEGRATION_CONTRACT.md`, “Not yet done”; `C7_CUTOVER_REQUIREMENTS.md`, gate 5). The contract is proposed rather than an accepted Chat migration decision, so Chat wiring is not a prerequisite for this bounded Tasks slice, but it remains before C7 cutover.

## E. Verdict

The archive and frozen boundary are intact, and the ordinary approval/dispatch/cancel chain retains Core and supervisor authority. The durable status path can nevertheless present an unverified execution as completed, a malformed record can abort reconnect, and the approval card does not show all arguments required by the C6 UI contract. Those are defects in the slice under review. The automated and native logs do not establish a real human Flutter approval or controlled power-loss qualification.
