## 4. Adversarial implementation review

The Phase 2B `verify_authority` and `SupervisedTurnRunner.begin` bind signed ticket, confirmed intent, arguments, and selection. The bridge checks the registry, executable hash and qualified model before `submit_task` ([bridge.py](../../uri-agent/uri_supervisor_bridge/bridge.py):186-220). Unique operation IDs, fenced attempts, reconciliation and receipt construction address ordinary replay and duplicate local execution. The single-threaded worker validates frame shapes and preserves pending state in memory. Source and tests cover stale ticket, swapped provider/model, duplicate operation, crash and resumed session cases; the environment prevented an independent full execution of those tests (section 9).

The qualification boundary is weaker than its own stated contract. The record digest is a plain recomputable hash. `probe_qualification.py` built a valid record for `model_a`, changed it to `model_b`, recomputed `record_sha256`, and both `validate_shape` and `revalidate` accepted it. It also replaced the referenced evidence file and observed that `revalidate` still succeeded. `revalidate` never reopens or checks the evidence file or its claimed digest. `compose_client` then promotes the record into the Phase 1 registry. The record has no client identity, client-root identity, policy identity, expiry, or trusted signer, so copying it into another client profile using the same executable and available live auth can inherit qualification. Changing its provider is constrained by `_spec_for`, but a same-provider different-model copy is accepted. See defects D1-D3 below.

The executable pin covers only the resolved `.cmd` shim ([qualification.py](../../uri-agent/uri_supervisor_bridge/qualification.py):210-228, [bridge.py](../../uri-agent/uri_supervisor_bridge/bridge.py):198). Replacing the Node executable or npm package behind unchanged shim bytes keeps both checks green; the actual launched program changes. This is a release-grade identity gap. The candidate’s own architecture acknowledges the limitation, so its `NATIVE_QUALIFIED` wording must be scoped to the shim. No real payload replacement was performed on the user's installation.

Run-scoped authentication is checked while composing the client; `SupervisorBridge.execute` uses the cached registry status and does not repeat `native_auth_probe` immediately before admission. Revocation/expiry while a worker remains alive is therefore detected only by the CLI when it runs. The test suite does not prove prompt invalidation of the displayed capability state. This is a status freshness gap rather than evidence of execution without provider credentials.

The approval digest is optional in the worker frame, and the frozen Flutter client sends `{turn_id, approve}` without it ([paired_runtime.dart](../../uri-agent/uri_ui/lib/services/paired_runtime.dart):177). The server ticket and pending turn still bind the approved arguments, so I did not find an argument substitution exploit from this alone. It does mean the claimed stronger displayed-digest echo is not exercised by the actual UI. Mid-run `turn_cancel` cannot be processed while `turn_decide` is executing: [worker_service.py](../../uri-agent/uri_supervisor_bridge/worker_service.py):38-53 only cancels pending turns, and [run_uri_supervised_worker.py](../../uri-agent/scripts/run_uri_supervised_worker.py):142-184 is a serial read/handle/write loop. The bridge can cancel from a second thread, but the worker protocol has no such concurrent path. Killing the worker is coarser and may leave uncertain effects. The copy-out verifier only checks a regular nonempty file and hashes it; it does not establish that arbitrary external actions have not happened. Therefore claims of duplicate **external** side-effect prevention must be limited to the task’s declared local-write effect and executor posture, not generalized to unrestricted tool use.

## 5. F-C1: governed Codex sessions

`--ephemeral` is **not required by a governing rule**. [ADR-018](../../uri-agent/URI_Model_Centric_Architecture_Docs/URI_ADR_018_MODEL_CENTRIC_ARCHITECTURE.md), the [model/runtime contract](../../uri-agent/URI_Model_Centric_Architecture_Docs/URI_MODEL_RUNTIME_CONTRACT.md), and [AI policy](../../uri-agent/URI_Model_Centric_Architecture_Docs/URI_AI_OPERATING_POLICY.md) require URI to own authority, state, and side-effect decisions. They do not forbid executor-private session storage. `_V1` harness research (`05_TARGET_ARCHITECTURE.md` §10; Paperclip reconnaissance §1, §5) treats the session as an opaque resume handle and URI's state as authoritative, but that research is not itself authorization. The implemented resume checks same task, previous recovery decision, executor registration, validated session ID, and current authorization. This is a defensible design if the external session is never trusted for permission or proof. A further input/context fingerprint is needed before resuming on changed task inputs; the current one-line task has no resolved input package to check. `--ephemeral` would remove resume, not repair that missing context boundary. The choice to persist Codex threads remains a privacy/product decision, not a rule-derived necessity.

## 7. Mid-run cancellation

**Needed for a complete user-visible supervised operations flow, but not explicitly listed as an independent 2D acceptance gate in an accepted Phase 2 plan.** The current [C6 contract](../../uri-agent/docs/plans/C6_UI_INTEGRATION_CONTRACT.md) describes approval/decline before dispatch; [Phase 2D architecture](../../uri-agent/docs/architecture/PHASE2D_COMPOSITION.md):97-99 itself records mid-run worker cancellation as missing. The harness strategy’s provider boundary includes interrupt/stop, but its index disclaims authorization. A production UI that offers cancellation of running work must implement a concurrent command/event channel with honest `execution_uncertain` settlement before claiming that operation. It is a remaining UI/operations slice, not grounds to pretend `turn_cancel` already does it.

## 8. Abrupt termination versus physical power loss

[The tests](../../uri-agent/tests/phase2d/test_abrupt_termination.py) inject `os._exit` at eight transition points and assert WAL/FULL, committed rows, integrity and recovery. That can verify process-death recovery; it cannot flush-loss or storage reordering. [The power-loss plan](../../uri-agent/docs/plans/PHASE2A_POWER_LOSS_TEST_PLAN.md) requires 200+ hard VM power-offs and a `synchronous=NORMAL` negative control. None was performed here. The 2A/2B reports explicitly list untested power loss among reasons **not to freeze the durable supervisor**. It is a freeze blocker for a claim of qualified power-loss durability. It is not a prerequisite for accepting a bounded, still-unfrozen 2D code slice. No reboot or power cycle was done.

## 10. Is 2D the last implementation slice?

**No.** The UI/operations slice is **REQUIRED IN PHASE 2** for a completed supervised product flow: C6’s contract explicitly leaves Chat connection behind a switch, the 2C plan explicitly calls for a worker/UI composition slice, the 2D source never switches Flutter, and the four-stage lifecycle requires live UI verification. Remaining work includes provider/model choice in the real UI, approval presentation with digest echo, authoritative progress/receipt and uncertainty, active cancellation, reconnect, auth/capability/quota status and human-in-the-loop events. Some details are not specified yet and need a bounded architecture/plan before implementation.

The richer CONTEXT / TASK PACKAGE capability is **PLACED IN A LATER, UNDATED PHASE**, rather than an accepted 2D closure condition. [Task Compiler placement](../../uri-agent/docs/architecture/PHASE2C_TASK_COMPILER_PLACEMENT.md) says design only and undated; no compiler, resolver-backed context pack, provenance manifest, authorized source/attachment narrowing, permission recheck or task-package generator is implemented in the Phase 2 packages. Phase 1 `IntentDiscovery.compile` merely maps confirmed `{instruction, expected_file}` to a one-line harness action. `_V1/docs/plans/M33_3_URI_BRAIN_ARCHITECTURE_PROPOSAL.md` §8 and `_V1/docs/research/URI_HARNESS_STRATEGY/05_TARGET_ARCHITECTURE.md` §6 describe a provenance-rich capsule with RAR/ARN/Graphify and policy fields, but the latter research expressly disclaims implementation authorization. These are real future architecture requirements for a general-purpose harness, not evidence that 2D delivered them or that a dated Phase 2 slice was accepted. Harness session content is cache, not URI context or authority.

Remaining sequence from current binding documents: repair qualification provenance and full executable identity; finish the actual UI/operations connection and live human path; complete provider profile authentication and native qualification; perform the VM durability study if claiming power-loss qualification; obtain independent audit and separately authorized C7 cutover. A richer context/task-package milestone follows its own four-stage lifecycle. No source establishes official 2E/2F numbering.

## 12. Verdict choice

**PHASE 2D REJECTED.** The persisted native qualification is forgeable by recomputing an unkeyed digest, its evidence file is not rechecked, and the executable pin does not cover the launched Node/package payload. Those are material to the claimed authorization boundary. The candidate additionally is not a byte-identical snapshot of the current tree due to its appended report, and the independent regression suites could not complete under this environment’s ACL restrictions. The implementation has useful bounded components and preserves the frozen Phase 1 tree, but cannot be accepted as a closure candidate on this evidence. Actual UI/operations work and qualification remain after remediation.
