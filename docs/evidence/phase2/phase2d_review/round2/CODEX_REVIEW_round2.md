## B. Round 1 repairs attacked

All results in this paragraph are **my own synthetic probes** in `qualification_probe.py`, independent of the implementer tests. A valid fixture record composed as `QUALIFIED`. Adding a model and recomputing the public digest yielded `RECORD_SIGNATURE_INVALID`; signing the edited record with another key yielded the same. Copying record and evidence into another synthetic client root yielded `RECORD_CLIENT_MISMATCH`; passing no trust anchor yielded `NO_TRUST_ANCHOR`. Editing the client-owned evidence yielded `EVIDENCE_HASH_MISMATCH`; deleting it yielded `EVIDENCE_MISSING`. A 60-second record checked at a time after expiry yielded `RECORD_EXPIRED`. A pinned synthetic payload replacement yielded `LAUNCH_CHAIN_HASH_MISMATCH`, and redirecting a pinned `node` through PATH yielded `LAUNCH_CHAIN_RESOLUTION_CHANGED`. Read-only discovery of the installed npm Codex chain returned 36 pinned files and a `node` resolution pin. The production `revalidate` check explicitly refuses native script launchers with an empty pin set at `qualification.py:406-408`; my attempted synthetic empty-chain record failed an earlier evidence-content check, so that particular rule was **source-inspected, not independently executed**.

The auth dispute D6 is resolved in favor of the repair response: `HarnessRegistry.selectable()` calls `discover()`, which calls the composition's auth probe on each selection (`harness.py:264-285`, `qualification.py:451-458`, `bridge.py:190-193`). My synthetic native-shaped record changed the injected auth answer from true to false after composition: `selectable()` changed from usable to `HARNESS_NOT_USABLE`. This did **not** log out of a real provider and does not prove its real CLI status output is always correct.

The repaired binding has an important remaining time-of-check gap. After successful composition, I deleted the evidence and the cached registry still returned selectable. I also composed a 60-second record at `expires_at - 1`; after the actual expiry, its registry remained selectable. The bridge checks auth, executable hash, launch-chain pins and model at each `execute`, but it does not reload the qualification record or recheck evidence or expiry (`bridge.py:190-208`). A long-lived worker therefore continues accepting a qualification whose stated validity has ended or whose evidence was removed. These probes used the actual `compose_client` registry, while the bridge behavior is established from the production call path; no external action was spawned in the probe.

The evidence-to-model binding is also incomplete. I built a **synthetic native-shaped** signed record with evidence reporting successful `model-a` only, but `models=[model-a, model-b]`. Composition reported `QUALIFIED` and bound both models. `_check_evidence` merely checks `ev.model in record.models` (`qualification.py:383-388`); the bridge accepts any model in the signed list (`bridge.py:207-208`). A legitimate qualification process currently passes one model, but the validator itself does not enforce that a model was tested before granting it. This is a meaningful schema/authority gap if records can be regenerated by any holder of the client key. The client signing key is protected by current-user DPAPI, not an independent qualification authority; I did not read or attempt to extract the real key. The stated same-user trust limit narrows the threat, but the record does not independently prove native qualification.

The launch-chain checks are substantial progress over a shim-only hash. They still have coverage and race limits. `npm_codex_launch_chain` explicitly pins Node, entry/package files and selected vendor suffixes (`qualification.py:117-151`), while direct executables return an empty additional chain (`:156-161`). OS-loaded libraries outside those paths and child programs are not covered; the architecture acknowledges this. Hashes are checked before the supervisor eventually spawns (`bridge.py:203-206,224-278`), without an atomic handle or immutability guarantee; a file changed between check and spawn could execute unpinned bytes. I did not replace a real installation or demonstrate that race, so this is a residual risk, not a proven exploit. The architecture file still says “pin covers the npm shim, not node or package” at `PHASE2D_COMPOSITION.md:141`, contradicting its own repaired qualification section and current code.

## E. Verdict

The repaired candidate is internally consistent and preserves Phase 1 bytes. The round 1 hand-edit/copy attacks are materially addressed, and D6 was an incorrect reading of the auth call path. Nevertheless, qualification expiry and evidence integrity are only checked when a long-lived worker composes its registry. A record that becomes invalid while the worker is alive remains usable, and the native evidence check allows a signed list to qualify untested models. Both affect the claimed qualification authority boundary. The exact verdict is therefore **PHASE 2D REJECTED**. The candidate should be repaired and independently re-reviewed; UI/operations work and user qualification still remain afterward.
