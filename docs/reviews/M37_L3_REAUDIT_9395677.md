## 7. Findings

**F-1 (LOW): git index flags, replace refs and `.git/info/exclude` hide changes from the guard.**
Three kinds of local git state make a tampered working tree look clean to `git diff` and `git ls-files --exclude-standard`: `--skip-worktree` or `--assume-unchanged` on a frozen file, a `git replace` of `5bbf738` (probed; the same would apply to `179fe10`, inferred), and an entry in `.git/info/exclude`. These bypasses are local-only and cannot travel on a branch: a fresh clone shows the true state. The M36-baseline half of the guard had the same exposure before the fix, so this is not a regression. The fix is cheap and stays test-only:
- run the guard's git calls with `--no-replace-objects`, or with the environment variable `GIT_NO_REPLACE_OBJECTS=1`;
- fail if `git ls-files -v` shows an `S` or lowercase flag on any frozen path;
- list untracked files using only the standard ignore patterns, not `.git/info/exclude`, or also list ignored files under the frozen prefixes (F-2).

**F-2 (LOW): ignored paths and stale bytecode can change frozen behaviour without the guard seeing it.**
The root `.gitignore` already ignores `__pycache__/`, `*.pyc`, `cache/`, `knowledge/` and `.env*` at any depth. So `uri_v1/edge/cache/__init__.py` becomes an invisible, importable package. A crafted `.pyc` whose header matches the source's mtime and size was loaded in place of the frozen `uri_v1/edge/repair.py`, and the guard stayed green. The root `.gitignore` is tracked but lies outside the six scanned roots, so it can add new hiding patterns. All of this is local-only and in the same class as the retained M37-L2 (Windows alternate data streams). A guard based on git cannot see bytecode. Record this as a limitation; a partial mitigation is to list `--ignored` files under the frozen prefixes, excluding `__pycache__`.

**F-3 (LOW): test infrastructure can be edited together with frozen code.**
These are visible in review, and the risk is inherent to a self-pin:
- editing the guard and the pin together passes, which the implementer disclosed;
- deleting the pin file passes too, because nothing asserts that the pin file exists (not disclosed explicitly);
- a root `pytest.ini`, `pyproject.toml` or `conftest.py` that deselects or patches the guard passes, because those files are outside the scanned roots. This was not disclosed, and it predates the fix.

Every one of these is committable, but it shows up in `git diff 5bbf738 --stat`. No in-repo check can close this fully; it needs an anchor outside the repo or a review rule. Recommendation for the re-freeze record: "The guard proves the frozen paths only while `tests/test_m37_edge_resolution.py`, `tests/test_m37_frozen_guard_pin.py`, `.gitignore` and the root pytest config are unchanged from the re-freeze commit. Reviewers check `git diff <re-freeze> -- <those files>`."

**F-4 (INFO): `docs/governance/URI_ACTIVE_MILESTONE.md` line 10 still says M37 is `CLOSED_FROZEN`.** The canonical `URI_STATE.yaml` says `REOPENED_FOR_AUTHORIZED_EDIT`. The mismatch is transitional and becomes correct again at re-freeze; the re-freeze commit should make sure both agree.

**F-5 (INFO): git quotes non-ASCII paths** (`"uri_v1/edge/\303\251vil.py"`). Such a path misses the new `unfrozen` prefix filter but is still caught by the `outside` filter, because a quoted path never matches an allowed prefix. The outcome is correct. Adding `-c core.quotePath=false` would make the report cleaner.

**F-6 (INFO, predates the fix): in an `autocrlf=true` checkout, the guard test fails at the M33.3 raw-byte S4 anchors.** It fails identically on `5bbf738`. This matters for Windows runs on Chetan's PC if `autocrlf` is on. It is unrelated to M37-L3.
