**New findings**
- **R1-01 HIGH (security):** C0 and C1 control characters and U+2800 (Braille blank) are not folded. They are invisible, and putting one between digit groups or inside a label defeats detection of cards, Aadhaar, SSN, PAN, IBAN, OTP and labelled credentials.
  - A full sweep of every non-letter, non-digit code point found 55 such control characters, plus U+2800.
  - On the TavilyProvider wire (httpx.MockTransport) these went out with status NO_RESULTS: `card 4111\x001111\x001111\x001111`, `card 4111\u28001111\u28001111\u28001111`, `wifi pass\x00word: Mango#2026!`, `aadhaar 2345\u28006789\u28000107`, `ssn 123\x0045\x006789` and `my otp\x00 482913`.
  - The same inputs passed `harness_private` (EXTERNAL_AGENT) and `Scheduler._sanitize_for_harness` unchanged.
  - Cause: `_invisible` only knows Cf plus a short default-ignorable list, and `_SPECIAL` never matches ASCII control characters.
  - This is the R1-01 / FB1-R1-01 class again, in a different Unicode category.
- **R1-02 MEDIUM, blocking (security):** the OD-1a gate checks only the text of the current turn, but the instruction sent to the harness is compiled from intent slots filled in earlier turns. I reproduced this on the real paired server stack (phase2d Stack, fake executor, run from a copy of the candidate in my work dir):
  - Turn 1 on the deterministic row (not gated): `use the harness to note the wifi password: Mango#2026!` returns INTENT_CLARIFICATION.
  - Turn 2 on the Claude harness row: `out.txt` returns INTENT_CONFIRMATION_REQUIRED.
  - Turn 3: `Confirm` returns approval_required, with instruction `note the wifi password: Mango#2026!`, and the run ends SETTLED_VERIFIED.
  - The control case (the same text in one harness-row turn) is refused PRIVACY_REFUSED.
  - Suggested fix: run the approval request's instruction through `prepare` before the card is returned, or at turn_decide / execution_begin.
  - I rated it MEDIUM rather than HIGH because of R1-03.
- **R1-03 MEDIUM, blocking (documentation):** threat model section 6 (E5/T7) and PC-8 say the working system's external-harness turns go through `run_uri_integrated_worker.py`. In the UI code they don't:
  - The only UI senders of turn_start / turn_intent are `paired_runtime.dart` and `supervised_runtime.dart`.
  - `supervised_runtime.dart` spawns `scripts/run_uri_supervised_worker.py` (a protected path with no privacy gate) and requires the preflight profile `phase2d-supervised`. The integrated worker reports `ws-integrated`.
  - So the UI harness path is still unprotected (OD-1), and "the vendor CLI carries the sanitized text" is overstated.
- **R1-04 LOW, non-blocking (owner policy):** CONFIDENTIAL markers give PRIVACY_GRANT_REQUIRED at EXTERNAL_AGENT, in both the harness gate and the scheduler, and no live surface can create a grant. So any harness task that mentions "confidential" can never run. This contradicts OD-5's "only REDACT/PSEUDONYMIZE/REFUSE are reachable". Separately, commit hashes in harness instructions are redacted unless a context word such as "commit" is nearby.
- **R1-05 LOW, non-blocking:** visible-form recall gaps: `card 4111+1111 1111 1111` (mixed separators) and `pass word: Mango#2026!` both passed.
