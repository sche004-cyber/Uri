## Diagnosis: R11-01 (hidden page text reaches the Brain), HEAD `fcfb465`

**The defect is still there at HEAD.** HEAD is the owner-decision D10 commit. It added a screenshot check as the new security boundary, but that check doesn't close the leak.

**What I ran.** I put the real `snapshot.js` in Playwright Chromium (1000×1500, the D10 test's own runner), then fed the result through `mk` / `grant(observe)` / `ask_and_wait` with the real screenshot. The probe is in `/tmp/uri_diag_D8/` (`page.html`, `probe.py`, `no_selection.png`). Each hidden payload sat on top of ordinary visible text:
- **z-index:-1:** a span under its parent's white background, positioned over that parent's own visible line.
- **SVG `fill="none"`:** text placed on top of a visible SVG text.
- **`-webkit-mask-box-image`:** a transparent mask box laid over a visible line.
- **`pointer-events:none` overlay:** a white overlay that carries its own visible text.
- **Striped background:** z-index:-1 text under a background of thin stripes.

**Result.** None of the payloads shows in the screenshot. All five reach `FakeClient.bodies` under "On-screen text (pixel-checked)" without a selection. After Ctrl+A, four of them also appear under "Selected text (pixel-checked)" (`ZNEG`, `MASKBOX`, `PEN` and `STRIPE` twice each; the SVG one dropped out of both), with `redactions={'no_ink': 4}`.

The R11 page's own techniques (screen-reader-only clip, height:0, max-height:0, text-indent, white overlay) are now removed by the in-page filter, even when placed over visible text. But D10 made the screenshot check the boundary, and that check is the part that fails.

**Root cause.** Every repair tests a stand-in for "the user can see this text", never the claim itself:
- **R10–R12 repairs:** a list of CSS hiding techniques in `snapshot.js`. Each repair added the techniques the last reviewer named.
- **D10 (HEAD):** `uri_assist/onscreen.py:54-94` keeps a piece if the screenshot shows enough contrast edges (`MIN_EDGE_DENSITY`, `EDGES_PER_CHAR`) inside the piece's own client rectangles. That proves *something* is drawn there, not that *these characters* are drawn.

The page controls both the hidden text and what is painted where that text sits. So it can always line hidden text up with other ink, and the doc's "residual limit" (`docs/assist/03_PERMISSION_AND_DATA_FLOW.md:83`, "hidden text whose rectangle overlaps other drawn ink … passes") is an open bypass.

The rectangles also come from `Range.getClientRects` (`snapshot.js:293`), which ignores paint order, masks and fill. And while text is selected, the browser repaints selected text in its own highlight colours. The in-page fallback for that (`sameAsBackground`) only handles a solid background colour.

**Why the earlier repairs missed it:**
- **`2de591e` (R10, +14 lines), `d5a9b41` (R11, +86) and `d029f60` (R12, +125)** each added the techniques the reviewer had just listed. Their regression tests replay only those payloads, so the next reviewer always found new ones (R12, then R13).
- **`fcfb465` (D10)** moved to a screenshot check, but its test page (`tests/assist/test_a0_d10_pixel_checked_text.py`, `PAGE`) places every payload on blank white space. Nothing tests hidden text sitting on visible ink. The thresholds were tuned on exactly that layout, and the known gap was written up as a residual limit instead of being tested.
