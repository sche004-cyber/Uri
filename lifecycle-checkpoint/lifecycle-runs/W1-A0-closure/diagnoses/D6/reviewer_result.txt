**Bottom line:** R11-01, R12-01 and R13-01 are the same defect. The in-page "hidden text" filter is a blocklist of known ways to hide text with CSS, and that list can never be complete. Each repair added only the hiding tricks the latest reviewer named, tested only those tricks, and widened the doc's claim. So the next review always finds another trick, and the doc is wrong about what is covered.

**What I checked at HEAD (d029f60).** I ran the current `snapshot.js` in real Chromium (1000x900 viewport, Ctrl+A) and took a screenshot. All five R13 payloads are absent from the screenshot, yet all five appear in both `snapshot.text` and `snapshot.selection`. The `hidden_text` count was 6, so the filter did not count them. The five are: text behind its parent's background via negative z-index, three SVG `<text>` cases (`fill` transparent, `fill-opacity` 0, `fill` none), and `-webkit-mask-box-image`. Three more cases leak and are not in the doc's "Not covered" list: `filter:blur(40px)`, `transform:rotateX(90deg)` and a 2px font. In code:
- `covered()` stops at `e.contains(p)` (`snapshot.js:226`). When the element on top is an ancestor of the text, the text counts as visible even though that ancestor's opaque background is painted over it.
- The paint check reads only `webkitTextFillColor`/`color` (`snapshot.js:240`). SVG text is painted with `fill`/`fill-opacity`, so it always passes.
- `masked()` reads only `maskImage`/`webkitMaskImage` (`snapshot.js:105`), never `webkitMaskBoxImage` or `mask-border`.

`bridge.py:66` then sends this text to the Brain under the heading "Visible text:", and `docs/assist/03_PERMISSION_AND_DATA_FLOW.md:77` says "hidden text dropped in page".

**Why the earlier repairs missed it** (`git show` of each):
- **2de591e (R10):** made the selection reuse the same per-element `visible()` check. It did not change what that check detects.
- **d5a9b41 (R11):** added per-text-node clip boxes, the legacy `clip` property, ancestor overflow, text-indent and occlusion. Those are exactly the R11 patterns. It also rewrote the doc row to list them, with a "Not covered" list of four items.
- **d029f60 (R12):** added effective opacity, `-webkit-text-fill-color`, `clip-path` geometry, `mask-image` and closed `<details>`. Again exactly the R12 patterns. It extended the doc's covered list, but the "Not covered" list only gained gaps the author already knew about.

The regression tests (`test_a0_r11_review_regressions.py`, `test_a0_r12_review_regressions.py`) contain only the reviewer's literal patterns, so they pass while the class stays open. No repair asked the general question: is this text actually painted? There is no pixel-based check anywhere, even though the extension already has `activeTab` (`manifest.json:6`), which is the permission `chrome.tabs.captureVisibleTab` needs.

**Proposed fix:**
1. Close the three R13 mechanisms at the code points above. A regression test for them already exists in my probe.
2. Add a check against real pixels:
   - `snapshot.js` returns each text chunk and selection piece with its client rects.
   - `popup.js` captures the visible tab and keeps a chunk only if its rect area contains pixels that differ from the surrounding background.
   - Text outside the viewport can't be checked this way, so it is dropped (fail closed).

   The Playwright test can do the same with `page.screenshot`. This catches all of the above, plus white-on-white text, `pointer-events:none` overlays, blend modes and blur, without listing them one by one.
3. Rename "Visible text" in `bridge.py` and correct the doc to describe exactly what is guaranteed.

**Decision for you:** Option 2 means the Brain sees only on-screen text, not everything below the fold. The alternative is to accept that the in-page filter is best-effort and rely on the untrusted data blocks plus the fact that A0 has no actions. That is a scope and risk-acceptance call. Without it the reviewer will keep raising a new variant every round, so I've set `needs_owner` to true.
