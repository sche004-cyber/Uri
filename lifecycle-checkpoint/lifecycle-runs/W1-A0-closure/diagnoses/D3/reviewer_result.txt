R1-01 keeps coming back because the number reader in `uri_web/evaluate.py` can't tell when it has split one amount into pieces, and both number checks trust whatever pieces it returns. Each repair added the reviewer's exact examples to the regex instead of fixing that. I re-ran the R5-01 probes at commit 52e852d and every one still reproduces; the probe script is `/tmp/d3probe/p.py`.

**What goes wrong**

1. **The number regex knows too few formats.** `_NUMBER` at `uri_web/evaluate.py:19` only accepts commas every three digits (`1,234,567`) or plain digit runs, and it never captures a sign. Anything else comes back in pieces:
   - `Rs 5,00,000` → `{'5','00000'}`
   - `Rs 5,00,00,000` → `{'5','00','00000'}`
   - `1 000 000` → `{'1','000'}`, while `1 500 000` → `{'1','500','000'}`
   - `-3.2%` and `−3.2%` → `{'3.2%'}`; `-12 degrees` → `{'12'}`
2. **Both checks then compare those pieces with subset tests:**
   - `verify` keeps a claim when the claim's numbers are a subset of the source sentence's (`uri_web/synthesize.py:99`).
   - `find_conflicts` skips any pair where one set is a subset of the other (`uri_web/evaluate.py:162`).
   
   A smaller amount split into pieces is very often a subset of a larger amount's pieces, so the defect fails open.

**Probe results at 52e852d** (claim vs source in the same sentence):

| Claim | Source | `verify` | Conflicts found |
|---|---|---|---|
| `Rs 5,00,000` | `Rs 5,00,00,000` | kept | 0 |
| `₹5,00,000` | `₹5,00,00,000` | kept | 0 |
| `1 000 000 euros` | `1 500 000 euros` | kept | 0 |
| `-3.2%` | `3.2%` | kept | 0 |
| `−3.2%` | `3.2%` | kept | 0 |
| `-12 degrees` | `12 degrees` | kept | 0 |

The same weakness also breaks things the reviewers haven't reported yet:
- `1,000.5` and `1,000.50` are treated as different numbers, so a correct claim is dropped. Values are compared as strings, not as numbers.
- `10,00,000 lakh` becomes `{'0','10'}`.

The user-facing text in `uri_web/surface.py:58` still says citations are "checked against the sources (wording, numbers, negation)".

**Why the earlier repairs missed it**

- **Repair 1 (16f75d8):** a one-line change to the lookbehind before the number (`(?<![\w.])` → `(?<!\d)`). Its tests in `tests/web/test_w1_r1_review_regressions.py` cover only the three strings the reviewer named: `Rs.500`, `approx.900` and `No.5`.
- **Repair 4 (52e852d):** added unit and scale handling after the number (`_SCALE`, `_UNIT`, `_fmt`) for R4-02. The comma grouping, missing sign handling and subset comparison were left as they were, so a fix aimed at lakh/crore words didn't touch lakh-style digit grouping. Its tests cover only the cases R4-02 listed (`$5bn` vs `$5m`, `2 crore` vs `2 lakh`, and so on).
- **Repairs 2 and 3 (627f6b9, 1615512):** changed only `uri_assist`, not `uri_web`.
- No repair added a test that every number in a sentence is read as one whole value, and nothing tests the subset rules against split numbers. All 36 R1-01/R4-02 regression tests pass at HEAD while R5-01 reproduces, so the tests passing proves nothing about this class.

**Proposed fix**

Change the number reader so it can't return fragments, rather than adding more examples to the regex:
- Accept Western, Indian and space/no-break-space grouping, each as one value.
- Keep a leading `-`, `−` or "minus" as part of the value.
- Turn each value into one exact canonical form (`Decimal` normalised, with unit and scale applied), so `1000.5` equals `1000.50`.
- If a digit run can't be read cleanly, mark the sentence as unverifiable instead of returning pieces. `verify` should then drop the claim and `find_conflicts` should not use the pair to rule out a conflict.

Add property-style regression tests over every grouping and sign form, for both `verify` and `find_conflicts`, in both directions. The R5-02 redaction finding in the history is a separate defect in `uri_assist`.
