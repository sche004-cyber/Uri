**What changed, per finding:**
- **R1-01 (forged verdict file):** the verdict is now read from the reviewer's result as returned in memory, never from `reviewer_result.txt`. `verify()` now rebuilds each round's result from the hashed raw output and also checks `reviewer_result.txt` against its recorded hash. A child process that rewrites the file afterwards can no longer change the verdict, and `verify()` reports the change. The docs (§6) wrongly said such writes were caught by the clean-worktree checks; that is corrected, and the correction is recorded in `LIFECYCLE_QUALIFICATION.md` rather than overwritten.
- **R1-02 (malformed findings):** if `findings` (or `prior_findings`) is not a list of objects, the whole result is treated as unparseable. The round becomes NO_RESULT and the run waits for the model; it is never ACCEPT. This applies to imported reviews too.
- **R1-03 (gate tests dropped from the proof):** class-based pytest ids now map to their test file, and Flutter ids resolve against the gate's working directory. If a gate test named by a gate finding can't be found, or has no configured regression runner, the repair is refused instead of the proof being quietly relaxed.
- **R1-04 (git hooks/config not anchored):** the hooks, config and `info/` state, plus replace refs, are now recorded when the plan is made. Any drift from that is BLOCKED as tamper for the owner, never a wait that resumes on its own. It is checked:
  - before every step (so before every worker);
  - right after every review;
  - in the evidence check.

  Only `unblock` of that particular block re-records the current state. The diagnosis worker now gets the same before/after integrity check, and the driver's git commands run with `core.fsmonitor=false`. Older runs without a recorded state get one recorded on their next `run`.

**Limits:**
- **Required test ids:** findings without an `id` are still accepted. An existing test (`test_r1_09`) uses findings with no id, and a finding missing its severity is already treated as blocking, so this can't produce a false ACCEPT.
- **Milestone refs not anchored:** the candidate, baseline and integration-target refs move legitimately during a run, so they are still checked per step rather than pinned to the plan.
- **Residual exposure:** a filter driver planted in git config plus attributes during a review could still run during the driver's post-review `git status`, before the drift check fires. It is now caught right after, but not prevented. I did not verify this path.
- **Graph not updated:** I did not run `graphify update .` because `graphify-out/` is outside the permitted paths.
- **Other R5 finding:** the R5 "non-deterministic baseline key" finding was not in this list and is not addressed.
