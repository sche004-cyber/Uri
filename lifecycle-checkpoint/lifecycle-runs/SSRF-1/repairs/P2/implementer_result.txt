I fixed R1-01: `fetch_url` no longer reports every refused fetch as a "private or local network" address. Only address-type refusals say that now; the others give the actual reason. The new tests fail on f44f70a and pass after the change.

**What changed:** one edit in `uri_core/tools/fetch_url.py`. A refused fetch now gets its message from a lookup on the refusal code instead of one fixed sentence:

| Refusal code | Message shown |
|---|---|
| `ADDRESS_NOT_PUBLIC`, `ADDRESS_TRANSITION_REFUSED`, `HOST_LOCAL_NAME`, `HOST_NUMERIC_AMBIGUOUS`, `HOST_SINGLE_LABEL` | "URI will not fetch that address (private or local network)." (unchanged) |
| `DNS_FAILED`, `DNS_EMPTY` | "URI could not reach that URL." (same wording as before SSRF-1) |
| `PORT_REFUSED` | "URI only fetches web pages on the standard ports (80 and 443)." |
| `SCHEME_REFUSED` (for example, a redirect to `ftp://`) | "Only http(s) URLs can be fetched." |
| `USERINFO_REFUSED` | "URI will not fetch a URL that contains a username or password." |
| `URL_INVALID`, `HOST_INVALID`, `HOST_MISSING`, `ADDRESS_INVALID` | "That URL is not valid." |
| any code not in the table | "URI refused to fetch that URL." |

`refusal_code` is still returned and no message includes the address. `uri_web/safe_fetch.py` needed no change, because its refusal codes already tell the cases apart.

**One difference from the reviewer's suggestion:** they listed `USERINFO_REFUSED` with the private-network codes. I gave it its own message, because a URL with a username and password is not a private address. Moving it back into the private group is a one-line change if you prefer that.
